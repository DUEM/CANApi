# CANApi

_C++ API for reading and sending the CAN messages on the DUSC vehicle. It is used by the Telemetry2021 telemetry board firmware (Arduino Mega 2560 with an MCP2515 CAN controller). Most of it is generated from the CAN message spreadsheet in [DUEM/CANTranslator](https://github.com/DUEM/CANTranslator)._

## What is in this repository

```
├── src
│   ├── CANHelper.hpp, CANHelper.cpp    hand-written: CANHelper::CANHandler, the MCP2515 wrapper
│   └── generated
│       └── CanApi.hpp, CanApi.cpp      GENERATED by CANTranslator: never edit by hand
├── examples/Basic                      example sketch (Basic.ino) and its UseMsgList.hpp
├── extras/ci/compile-all-messages.sh   compiles with every message enabled (used by CI)
├── .github/workflows/build.yml         CI: builds for the Mega 2560 with avr-gcc
├── library.properties                  Arduino library metadata
└── .gitattributes                      marks src/generated/ as generated for GitHub
```

| File | Contents |
|---|---|
| `src/generated/CanApi.hpp` | One packed struct per CAN message (e.g. `CANHelper::Messages::Tritium::Velocity`), its `CAN_ID_`, `CAN_DLC_` and `CAN_META_` macros, the `CastedCANPayload` union of all of them, the `CANHelperBuffer` union and the `CanMsgHandler` class that declares one `processMessage()` per message |
| `src/generated/CanApi.cpp` | `CANHandler::DispatchMsg()`: a `switch` on the CAN ID that calls the right `processMessage()` (byte-swapping each field of big-endian messages first), then `processAll()` |
| `src/CANHelper.hpp`, `src/CANHelper.cpp` | `CANHelper::CANHandler`: `read()`, `testRead()`, `send()`, `setCanMeta()`, `reverseBytes()`, the `LATEST_MSG*` macros, and the lookup of `UseMsgList.hpp` |

**Do not edit `src/generated/` by hand.** `ApiGen/CanApiGen.py` in CANTranslator writes these files, and the next run overwrites them. To add or change a message, follow [How to add or change a CAN message](https://github.com/DUEM/CANTranslator#how-to-add-or-change-a-can-message) in the CANTranslator README.

```
 CANTranslator: config/CANConfig.xlsm  (one row per CAN message)
   │  python3 ApiGen/CanApiGen.py -c config/CANConfig.xlsm -h CANApi/src/generated/CanApi
   ▼
 this repository: src/generated/CanApi.hpp/.cpp  (+ hand-written src/CANHelper.hpp/.cpp)
   │  git submodule (or Arduino/PlatformIO library)
   ▼
 Telemetry2021 firmware: Telemetry/src/CANApi/
```

## Requirements

* The [autowp arduino-mcp2515](https://github.com/autowp/arduino-mcp2515) library (`mcp2515.h`, which provides `can_frame`, `MCP2515`, `CAN_SPEED`)
* A GCC-compatible compiler: the code uses `__attribute__`, `__has_include`, the `__u8` type from `mcp2515.h`, and anonymous structs inside unions. It compiles as C++11 with GCC
* A `UseMsgList.hpp` that chooses the messages (see below)

## Adding it to a firmware project

There are two ways to use it.

**As a submodule in the sketch** (what Telemetry2021 does; works in the Arduino IDE):

```shell
cd <sketch folder>
git submodule add git@github.com:DUEM/CANApi.git src/CANApi
git -C src/CANApi checkout v1.0      # or the version you need, see Versions
```

Put `UseMsgList.hpp` in the sketch folder and `#include "src/CANApi/src/CANHelper.hpp"`. The Arduino IDE compiles everything under the sketch's `src/` folder, and `CANHelper.hpp` finds `UseMsgList.hpp` three folders up.

**As a library** (PlatformIO, or arduino-cli): add this repository as a library, e.g. in `platformio.ini`:

```ini
lib_deps =
  https://github.com/DUEM/CANApi.git#v1.0
  autowp/autowp-mcp2515
build_flags = -I include          ; the folder that holds UseMsgList.hpp
```

and `#include <CANHelper.hpp>`. The library's own `.cpp` files must be able to find `UseMsgList.hpp`, so its folder has to be on the include path. Alternatively, define `CANAPI_CONFIG_FILE` as the file to use, e.g. `-DCANAPI_CONFIG_FILE='"MyMsgList.hpp"'`. **The Arduino IDE cannot do either for an installed library**, so with the Arduino IDE use the submodule.

`CANHelper.hpp` uses the first of these that exists: `CANAPI_CONFIG_FILE`, then `UseMsgList.hpp` on the include path, then `../../../UseMsgList.hpp` (the sketch folder, for the submodule layout). If none exists, the build stops with an `#error` saying so.

### Choosing messages: `UseMsgList.hpp`

Nothing is compiled in unless you ask for it. Define one `USE_MSG_<Group>_<Message>` macro for each message the firmware uses. The value is 2 bits:

| Value | Meaning | You get |
|---|---|---|
| `0b01`, or no value | Write only: the board sends it, or just uses the struct | the struct, the `CAN_ID_`/`CAN_DLC_`/`CAN_META_` macros and `as_<Group>_<Message>` in the payload union |
| `0b10` or `0b11` | Read (or read and write): the board handles it when received | all of the above, plus a `processMessage()` declaration and a `case` in `DispatchMsg()`. **You must define that `processMessage()`**, or the link fails |

`#define PROCESS_ALL_MSG` adds `processAll()`, which is called for every received frame, recognised or not, after any `processMessage()`.

```cpp
// UseMsgList.hpp: 2-bit values, MSB = read, LSB = write
#define USE_MSG_Telemetry_MpptPollJaved 0b01
#define USE_MSG_DriverControls_SpeedValCurrVal 0b10
#define PROCESS_ALL_MSG
```

The message names are listed in `src/generated/CanApi.hpp` (search for `#ifdef USE_MSG_`).

### Using it

[examples/Basic/Basic.ino](examples/Basic/Basic.ino) is a complete sketch. In short:

```cpp
#include "src/CANApi/src/CANHelper.hpp"               // or <CANHelper.hpp> when used as a library

CANHelper::CANHandler canHandler(10, CAN_125KBPS);    // MCP2515 chip select pin, bus speed (assumes an 8 MHz crystal)

void loop() {
  canHandler.read();          // polls the MCP2515; if a frame has arrived, dispatches it
}

// Sending: fill a buffer through the message struct, set its ID and DLC, send
void pollMppt() {
  CANHelper::CANHelperBuffer poll;
  poll.payloadBuffer.as_Telemetry_MpptPollJaved.Blank = 0;
  canHandler.setCanMeta(poll, CAN_META_Telemetry_MpptPollJaved);
  canHandler.send(poll);
}

// Receiving: one definition for each message whose read bit is set
void CANHelper::CanMsgHandler::processMessage(CANHelper::Messages::DriverControls::SpeedValCurrVal& msg) {
  // msg.DriverSetSpeed, msg.DriverSetCurrent
}

// Every frame, if PROCESS_ALL_MSG is defined. msg.raw is the can_frame, exactly as received
void CANHelper::CanMsgHandler::processAll(CANHelper::CANHelperBuffer& msg) {
}
```

Check the chip select pin and bus speed for your board.

Inside `CanMsgHandler`/`CANHandler` member functions (including your `processMessage()` and `processAll()`), `LATEST_MSG`, `LATEST_MSG_ID`, `LATEST_MSG_DLC` and `LATEST_MSG_DATA` give the last received frame, its ID, its DLC and its payload union. They expand to `this->messageRead...` and do not work anywhere else. For big-endian messages, `LATEST_MSG_DATA` holds the bytes as received. The byte-swapped values are in the `msg` passed to `processMessage()`.

`CANHandler::testRead(frame)` dispatches a `can_frame` as if it had been received, which is useful for testing handlers without a CAN bus.

### How decoding works

`CANHelperBuffer` is a union of the raw `can_frame` and a padding array followed by `CastedCANPayload`, so `payloadBuffer` sits exactly on top of `can_frame.data`. A received frame is read straight into the buffer, and `processMessage()` gets a reference to the right struct in the union, without copying. The structs are `packed`, so they match the byte layout on the bus on any compiler. Big-endian messages (the Orion BMS) are the exception: each multi-byte field is byte-swapped in a copy, and the copy is passed to `processMessage()`.

## Versions

Releases are git tags. Each Telemetry2021 branch pins a commit through its submodule.

| Tag / branch | Files | Notes |
|---|---|---|
| `v0.4` | `CanApiv04.hpp/.cpp` | Older API: one struct per message deriving from `CANMsg`, free `processMessage()` functions. **Not source compatible with v1.0.** Telemetry2021 `PERI-DEVELOPMENT-TPB-1126`, `ESC-CODE`, `BWSC2023` and `DUSC2024` use `8d050b1`, the commit after `v0.4` |
| `v1.0-beta` to `v1.0-beta.4` | `CanApiv10.hpp/.cpp` in the top folder | `CANHandler` class, member `processMessage()`, big-endian support (beta.3 onward). `v1.0-beta.4` (`fe308f7`) is used by Telemetry2021 `nick-22Library` |
| `v1.0` (TPB, 11/26) | `src/CANHelper.*`, `src/generated/CanApi.*` | The Nov 2026 fixes and the new layout. See the changelog below |

### Moving firmware from `v1.0-beta.4` to `v1.0`

1. Change `#include "src/CANApi/CANHelper.hpp"` to `#include "src/CANApi/src/CANHelper.hpp"`.
2. Rename any of these messages the firmware uses (`nick-22Library` uses none of them): `Tritium_StausInformation` became `Tritium_StatusInformation`. The Orion and Testbed messages have new, unique names (see the changelog).
3. Do not call `DispatchMsg()` directly. It is now `protected`; use `read()` or `testRead()`.
4. Build the firmware and test it on the board.

## Changelog

**v1.0** (Nov 2026; the fixes are on branch `PERI-DEVELOPMENT-TPB-1126-fixes`, the layout on `TPB-1126-restructure`)

* Files moved: `CANHelper.*` to `src/`, and the generated `CanApiv10.*` to `src/generated/CanApi.*` (the version is in the tag, not the file name). The generated files now start with a `GENERATED FILE: DO NOT EDIT` notice.
* `UseMsgList.hpp` is no longer found only at `../../UseMsgList.hpp`: see [Adding it to a firmware project](#adding-it-to-a-firmware-project).
* Arduino library metadata, an example sketch and an avr-gcc CI build were added.
* `CANHandler::DispatchMsg()` is `protected`.
* Messages that shared a name now have unique ones, so they can all be enabled: Orion 0x6B0 `PackParametersDefaultId`, 0x6B1 `CellTempsDclDefaultId`, 0x700 `PackParameters`, 0x701 `CellTempsDcl`, 0x702 `CellVoltages`. Rows marked inactive in the spreadsheet (Testbed 0x1B1, 0x1B2; Tritium 0x60A, 0x60D) are no longer generated. Tritium 0x601 is now `StatusInformation`.
* Big-endian (Orion) messages are decoded correctly: each field is byte-swapped, in a copy, so `processAll()` gets the frame as received. Before, the whole payload was reversed in place, which also reversed the field order.
* `reverseBytes()` is fixed. It used to swap most bytes twice and read one byte past the payload.
* Structs are `packed` as well as `aligned(8)`, so the layout matches the bus on any compiler (no change on the AVR).
* A `USE_MSG_` macro with no value now means write only, instead of being a compile error.

The full list, with the reasons, is in [Changes made in November 2026](https://github.com/DUEM/CANTranslator#changes-made-in-november-2026) in CANTranslator.

## Testing

* **CI** ([.github/workflows/build.yml](.github/workflows/build.yml)), on every push and pull request: builds [examples/Basic](examples/Basic) for the Arduino Mega 2560 with arduino-cli and the real MCP2515 library, then compiles the library with **every** message enabled for reading and writing ([extras/ci/compile-all-messages.sh](extras/ci/compile-all-messages.sh)).
* **CANTranslator's tests** (`pytest` there) check that `src/generated/` is exactly what the spreadsheet generates. They also compile it with `g++` on a laptop, against a stub `mcp2515.h`, and decode test frames.

To run the all-messages compile locally without the AVR toolchain, from this folder with CANTranslator next to it:

```shell
CXX=g++ CXXFLAGS="-std=gnu++11 -Wall -Werror" INCLUDES="-I ../CANTranslator/Tests/stubs" extras/ci/compile-all-messages.sh
```

Neither replaces building the actual firmware and trying it on the board.
